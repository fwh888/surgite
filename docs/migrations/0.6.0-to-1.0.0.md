# Upgrading standup-gen 0.6.0 → 1.0.0

1.0.0 is the **multi-tenant / orgs** release. It introduces organisations to the
data model: two new tables (`orgs`, `org_members`), a `personal_org_id` on every
user, and a nullable `org_id` on every per-user table. Each existing user gets a
private **personal org** they own, and all their data is associated with it.

The **API surface is unchanged**. Every 0.6.0 endpoint keeps behaving exactly as
before — it now resolves to the caller's personal org under the hood. The org
API and UI (creating shared orgs, inviting members, switching org) are additive
and arrive later in the 1.0.0 line; this migration is only the data-model change
that makes them possible. The snapshot-tested OpenAPI document is byte-identical
to 0.6.0 for the endpoints that existed then, so the stability promise in
[api-stability.md](../api-stability.md) holds.

> **Back up the database first.** This migration alters every table. Use
> `scripts/backup.sh` or a plain `pg_dump`. There is a downgrade
> (`alembic downgrade -1`), but a backup is faster and safer if something is off.

## Running it

No manual steps. The standard deploy runs the migration:

```
alembic upgrade head
```

On a fresh 0.6.0 database this runs in well under a second. There is no config
to change, no new env var, and no CLI change for the orgs migration itself —
a 0.6.0 install that pulls 1.0.0 and runs the migration keeps working
unchanged. (1.0.0 additionally renames the project to `surgite`, which does
change configuration — the `STANDUP_*` env vars, the CLI command, and some
defaults. That is a separate, one-time step covered in the
["Upgrading from standup-gen (pre-rename)"](../self-host.md#upgrading-from-standup-gen-pre-rename)
section of the self-hosting guide.)

## What the migration does

1. Creates `orgs (id, name, slug, created_at, deleted_at)` and
   `org_members (org_id, user_id, role, joined_at)`.
2. Adds a nullable `personal_org_id` FK to `users`.
3. For **every existing user**, creates one personal org (name and slug derived
   from the email local-part, disambiguated with a `-2`, `-3`… suffix on slug
   collision), adds an `org_members` row with `role = 'owner'`, and points
   `users.personal_org_id` at it.
4. Adds a nullable `org_id` FK to the nine per-user tables — `repos`,
   `sessions`, `invites`, `prompt_settings`, `shared_summaries`, `api_keys`,
   `provider_keys`, `password_resets`, `audit_log` — and backfills each row to
   its owner's personal org. (`commits` is intentionally left out: a commit's
   org is derivable via `repo_id → repos.org_id`. Audit rows from pre-auth
   events, which have no actor, keep a null `org_id`.)
5. Drops the `NOT NULL` on `owner_id` for `repos`, `prompt_settings`, and
   `shared_summaries`, so a future org-owned resource can have `owner_id = NULL`
   with `org_id` set. Every existing row keeps its `owner_id`.

It runs in a single transaction on Postgres.

## Verifying afterwards

```sql
-- Every user has exactly one personal org.
SELECT count(*) AS users, count(personal_org_id) AS users_with_org FROM users;
-- Every per-user row has a non-null org_id (repos shown; same for the others).
SELECT count(*) AS repos, count(org_id) AS repos_with_org FROM repos;
-- One owner membership per personal org.
SELECT count(*) AS owner_memberships FROM org_members WHERE role = 'owner';
```

`users == users_with_org`, `repos == repos_with_org`, and
`owner_memberships == users` on a healthy upgrade.

## Rolling back

`alembic downgrade -1` drops `org_members`, `orgs`, the `personal_org_id`
column, and every `org_id` column, and restores the `NOT NULL` on the three
`owner_id` columns. Your original rows are left intact.

This rollback is **lossy for org data only**: any shared orgs, memberships, or
org-scoped resources created after the upgrade are dropped along with the tables.
Personal data (repos, commits, settings, summaries) is untouched because it is
still keyed on `owner_id`. If you have created shared orgs, back up before
downgrading.
