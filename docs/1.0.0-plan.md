# 1.0.0 Plan

Targeted at **v1.0.0** — the **multi-tenant / day-one orgs** release.

Builds on the 0.6.0 baseline, which shipped the API stability contract
(snapshot-tested OpenAPI, `docs/api-stability.md`, `docs/security-support.md`,
the deprecation procedure, and the CLI keyring + email-delivered password
reset that closed the last UX gap to "polished product"). 0.6.0 was the
release that made the public surface safe to commit to. 1.0.0 freezes that
commitment by *using* it: orgs land on top of the frozen 0.6.0 surface
without breaking the stability promise, and the API spec from 0.6.0 is
unchanged in this release. (The historical 0.5.0 and 0.6.0 plans are
archived at `docs/releases/0.5.0-plan.md` and `docs/releases/0.6.0-plan.md`.)

This is the first release that introduces a **breaking change in the data
model**: every per-user table gains a nullable `org_id` foreign key, and
`owner_id` becomes optional on the tables where it's the only scope key
today. The public *API* surface stays stable — the existing endpoints
keep working (they now resolve to the user's *personal* org) and the new
`/orgs/*` endpoints are purely additive. The break is in the database
schema and in the auth scope; both are documented in
`docs/migrations/0.6.0-to-1.0.0.md` (delivered as part of Slice 1).

The plan is organised by theme rather than by file, with each item
carrying an effort estimate (**S** ≤ half a day, **M** = 1–2 days, **L** =
3+ days) and a priority (**P1** = blocking for the release / blocking for
1.0.0, **P2** = should land in 1.0.0, **P3** = nice-to-have, defer to
1.0.1 or 1.1.0 if needed).

Estimated total: **~18–22 dev days** across **three slices** (data model +
migration → orgs API + UI → stability freeze + 1.0.0 release cut). The
slice count mirrors 0.5.0 and 0.6.0's three-PR cadence. Effort tally
across the 21 items below: 10×S + 9×M + 2×L. 1.0.0 is deliberately
*larger* than 0.6.0 (~10–15 dev days) because the org model touches 9
tables and a real migration, which is genuinely more work than the
0.6.0 snapshot/CLI-keyring surface.

## Out of scope (explicitly deferred)

These are 1.1.0+ candidates that would be tempting to fold in here but
shouldn't. Listing them now so we don't get scope-crept.

- **OIDC / SSO** (Google, GitHub, GitLab, generic OIDC). 1.1.0 scope.
  The 0.5.0 plan and 0.6.0 plan both designed the auth backend so OIDC
  slots in by replacing `get_current_user` with an OIDC-verifier-first
  version falling back to the cookie. That extension point is intact and
  unused. Implementing it well requires provider config UX, account
  linking (a user may sign up with email-password and later link Google),
  and session-vs-token semantics — all enough work to be a real PR.
  1.1.0 carries it.
- **Billing / Stripe / SaaS self-signup.** 1.1.0+ scope. 1.0.0 is
  self-host only; operators continue to be the entity that controls user
  creation. The moment billing is added, the data model has to carry a
  per-org subscription state, and that touchpoint shouldn't ride along
  with the org cutover.
- **Per-org AI provider keys.** 1.1.0 scope. 0.5.0's `ProviderKeyRow`
  is keyed by `user_id`; in 1.0.0 it gains a nullable `org_id` and
  resolves to "user's key, falling back to org's key, falling back to
  personal key" — but org-scoped key management UI is a 1.1.0 PR.
- **Per-org rate limits, quotas, and audit log scoping.** 1.1.0 scope.
  `AuditLogRow` already records `user_id`; making it `org_id`-scoped
  requires a query rewrite in the admin UI. Not blocking for 1.0.0
  because the org admin can use the existing user-scoped audit log
  filtered to org members.
- **Team / sub-org nesting.** 1.0.0 has exactly two scopes: user and org.
  No teams within orgs. If a deployment needs sub-groups, that's a
  separate feature, not a nesting of this one.
- **Org-level summary history / shared-summaries within an org.** 1.1.0
  scope. `SharedSummaryRow` in 1.0.0 is `owner_id`-scoped, same as 0.6.0;
  orgs get a "shared within the org" flag in 1.1.0.

## Slice 1 — Org data model + migration

The first slice introduces the org concept to the database. After this PR,
the schema is multi-tenant-ready: every per-user table has a nullable
`org_id` FK, every existing user has a personal "default" org they own,
and all existing API endpoints resolve to that personal org. The goal is
to make the data model multi-tenant without making the API multi-tenant
yet — slice 2 is the API/UI work. The break is invisible from the API
perspective (every endpoint behaves the same as 0.6.0) and is only
visible in the schema and the new `migrations/` doc.

### Schema + migration

1. **schema: add `orgs` and `org_members` tables** — *M, P1*

   New tables:
   - `orgs (id, name, slug, created_at)` — slug is the URL-safe org handle
     (unique, lowercase, 3–32 chars, `[a-z0-9-]`). `name` is the display
     name (editable). No `owner_id` — every org has at least one
     `org_members` row with `role = 'owner'`.
   - `org_members (org_id, user_id, role, joined_at)` — composite PK
     `(org_id, user_id)`. `role` is an enum: `owner | admin | member`.

   `get_session()` adds nothing new here — the rows go through the same
   SQLAlchemy `Base` as the existing tables. The alembic migration
   (`alembic/versions/<sha>_orgs_and_members.py`) creates both tables
   inside a single transaction. **Don't split the table creation across
   migrations** — a partial state where `orgs` exists without
   `org_members` (or vice versa) leaves the data model in a half-state
   that no slice can build on.

2. **schema: backfill a personal org for every existing user** — *M, P1*

   The migration's second half creates one default personal org per
   existing user (named after the user's email local-part, slugified) and
   adds an `org_members` row with `role = 'owner'`. For new users created
   post-migration, the create-user path (in `backend/auth.py`) creates
   the personal org in the same transaction. **Gotcha:** the backfill
   must use the same code path the create-user path uses — implement
   `create_personal_org(user)` in `backend/auth.py` and call it from
   both the migration and the create-user handler, so the invariants
   (slug format, member role, name) are identical.

3. **schema: add nullable `org_id` FK to all per-user tables** — *L, P1*

   The migration adds a nullable `org_id` FK to: `repos`, `sessions`,
   `invites`, `prompt_settings`, `shared_summaries`, `api_keys`,
   `provider_keys`, `password_reset_tokens`, `audit_log`. That's 9
   tables. The migration is a single alembic file with one
   `op.add_column` per table inside a single transaction. **Gotcha:**
   `invites` and `password_reset_tokens` already have `user_id` columns
   for `created_by` / `redeemed_by`; `org_id` on those is the *issuing
   org* (a personal org for self-issued, an org for admin-issued). Don't
   conflate `org_id` with `user_id` on these tables — they're different
   semantics. The backfill is a single `UPDATE` per table setting
   `org_id = <user's personal org id>`; for `invites` / `password_reset_tokens`
   it's `org_id = created_by_user.personal_org_id`.

4. **schema: drop the `NOT NULL` on `owner_id` / `user_id` where `org_id`
   is the new scope** — *S, P1*

   For `repos`, `prompt_settings`, `shared_summaries`, `api_keys` the
   `owner_id` column becomes nullable (an org-scoped resource has
   `owner_id = NULL`, `org_id = <org>`). For `provider_keys`,
   `password_reset_tokens`, `sessions`, `audit_log` the existing
   `user_id` column stays NOT NULL (every action still has a human
   actor; the *org context* is the new dimension). For `invites`,
   `created_by` stays NOT NULL but becomes nullable when invites are
   org-issued by an admin who isn't the user — see Slice 2.

   **Gotcha:** before dropping NOT NULL on `owner_id`, the migration
   must verify no `CHECK` constraint or application code in 0.6.0
   assumes `owner_id IS NOT NULL`. Run `git grep "owner_id"` across
   `backend/` and `tests/` and surface every site that reads it
   unconditionally — those sites need to learn about `org_id` in
   Slice 2. The migration itself doesn't change application code; it
   only changes the schema. Application-level changes are in Slice 2.

### Auth + scope resolution

5. **auth: introduce an `EffectiveScope` resolver** — *M, P1*

   New module `backend/scope.py` exposing `resolve_scope(user, db) ->
   EffectiveScope` where `EffectiveScope` is a dataclass with
   `{user_id, personal_org_id, current_org_id, current_org_role}`. The
   `get_current_user` dependency still returns a `UserRow`, but it
   additionally stuffs the `EffectiveScope` into `request.state` so
   route handlers can read it without re-querying. The 0.6.0 endpoints
   read `request.state.scope.personal_org_id` and pass it as `org_id`
   on every insert/update. **This is the wiring that makes Slice 1
   invisible from the API perspective** — no endpoint changes its
   signature or response shape; the only change is that inserts now
   also set `org_id`.

6. **auth: per-route `assert_org_member` guard** — *S, P1*

   New dependency `assert_org_member(org_id, db, current_user)` that
   404s if the org doesn't exist and 403s if the current user isn't a
   member. In Slice 1 every existing endpoint still passes the user's
   personal org, so the guard is a no-op for those endpoints; in
   Slice 2 the new `/orgs/{org_id}/*` routes use it for real. Putting
   the guard in Slice 1 means the 0.6.0 endpoints can opt in
   incrementally without a big-bang refactor.

### Documentation

7. **docs: write `docs/migrations/0.6.0-to-1.0.0.md`** — *S, P1*

   The migration doc is the operator-facing deliverable for Slice 1.
   It covers: what the alembic migration does, how to run it
   (`alembic upgrade head` — no manual steps), what to verify
   afterwards (every existing user has a personal org; every per-user
   row has a non-null `org_id`), and the rollback story (`alembic
   downgrade -1` works, but the operator must explicitly accept that
   downgrade drops the `org_id` columns). Linked from `docs/self-host.md`
   in the "Upgrading" section and from the CHANGELOG.

**Slice 1 exit criteria:** the alembic migration runs cleanly on a
copy of the 0.6.0 production database; after migration every
existing user has exactly one `orgs` row (their personal org) and
every per-user table row has a non-null `org_id`; the full 0.6.0 test
suite (259 tests) still passes with no test changes; the existing
`/repos`, `/commits`, `/summary`, `/settings/prompt` endpoints behave
identically from the API surface (verified by the snapshot test);
`docs/migrations/0.6.0-to-1.0.0.md` is published.

## Slice 2 — Orgs API + UI

The second slice exposes the org concept to API consumers and to
the web UI. After this PR, an authenticated user can create an
org, invite users, switch the active org, and see org-scoped data
in the UI. The 0.6.0 endpoints continue to work and now resolve
to the user's *current* org (which defaults to personal). New
endpoints are additive: `POST /orgs`, `GET /orgs`, `GET /orgs/{id}`,
`PATCH /orgs/{id}`, `POST /orgs/{id}/members`, `DELETE
/orgs/{id}/members/{user_id}`, `PATCH /orgs/{id}/members/{user_id}`,
`POST /orgs/{id}/invites`, `POST /orgs/{id}/switch`. The OpenAPI
snapshot test gets new entries; `docs/openapi.json` is regenerated
and committed; the stability promise is *not* broken (additive
endpoints on a frozen surface are explicitly allowed by
`docs/api-stability.md`).

### API

1. **API: `POST /orgs` and `GET /orgs`** — *M, P1*

   `POST /orgs` creates a new org. The creating user becomes `owner`.
   Body: `{name, slug}` (slug is optional — auto-derived from name
   and disambiguated with a numeric suffix on conflict). Response:
   the new `OrgRow` plus the creator's `OrgMemberRow`. `GET /orgs`
   returns the list of orgs the current user is a member of, with
   the member's role on each. 403 if the current org is suspended
   (a future feature; the column is reserved but not exposed yet).
   `GET /orgs/{id}` returns the single org plus the caller's
   membership row.

2. **API: `PATCH /orgs/{id}` and `DELETE /orgs/{id}`** — *M, P1*

   `PATCH` allows name and slug change (slug uniqueness enforced).
   403 if the caller is not `owner` or `admin`. `DELETE` is
   restricted to `owner` and requires a confirmation header
   (`X-Confirm-Delete: <org-name>`) to prevent accidental
   self-deletion. Soft-delete via a `deleted_at` column (the
   alembic migration in Slice 1 already added it as nullable);
   the row stays in the table so existing references in
   `audit_log` and `shared_summaries` remain valid. A hard-delete
   CLI tool is a 1.1.0 item.

3. **API: `/orgs/{id}/members` and `/orgs/{id}/invites`** — *L, P1*

   Four endpoints: list, add, change role, remove. The add path
   accepts either a `user_id` (for adding an existing user) or an
   `email` (which creates an invite if the email isn't a user yet).
   Role changes from `owner` require transferring ownership first
   (a separate `POST /orgs/{id}/transfer` endpoint that requires
   the new owner's consent — they have to accept the transfer
   before the original owner can downgrade). Invite redemption
   extends the existing `InviteRow` model with a nullable `org_id`
   column (already added in Slice 1's migration).

4. **API: `POST /orgs/{id}/switch` and the active-org cookie** — *M, P1*

   The user's "active org" is stored as a cookie (signed, httpOnly,
   same security posture as the session cookie). `POST /orgs/{id}/switch`
   sets the cookie to the target org. The `resolve_scope()` function
   from Slice 1 reads the cookie and returns the matching
   `current_org_id`; the absence of the cookie means
   `current_org_id = personal_org_id`. The cookie is invalid if the
   user is no longer a member of the org it points to — `resolve_scope`
   403s in that case (and clears the cookie).

   **Gotcha:** don't store the active org in the JWT/session token.
   Sessions are long-lived (cookie lifetime) and an org suspension
   has to take effect immediately, not on the next login.

### UI

5. **frontend: org switcher in the chrome** — *M, P1*

   The web UI's top bar gets an org switcher dropdown. It lists the
   user's orgs with the role badge (owner / admin / member). The
   active org is highlighted. Switching fires `POST /orgs/{id}/switch`
   and reloads the page (so all current-org-scoped data refetches).
   A Svelte store (`currentOrg` writable) holds the active org for
   components that need it without re-querying. The existing
   user-scoped views (`/repos`, `/settings`, etc.) re-bind to the
   active org without route changes.

6. **frontend: `/orgs/new` and `/orgs/{id}` pages** — *M, P1*

   Two new pages. `/orgs/new` is a form (name + slug) with a
   client-side uniqueness check (debounced 300ms). `/orgs/{id}`
   is the org admin page: name, slug, members list, invites list,
   and (for owner only) the "Delete org" button with the
   confirmation header wired up client-side. Both pages follow the
   same component conventions as the existing admin pages (Svelte
   5 runes, no Svelte 4 syntax, the existing AGENTS.md rule).

7. **frontend: invite-redeem page for org invites** — *S, P1*

   The existing `/signup?token=...` flow gets an `org_id` query
   parameter (set by the email link). The redeemed invite adds the
   user to the org in the same transaction that creates the user
   account (or upgrades an existing user). The success page links
   to the org admin page.

### Tests + docs

8. **test: full org API test suite** — *M, P1*

   Tests for every new endpoint: create, list, get, patch, delete
   (with and without confirmation header), member add/remove/role
   change, ownership transfer, invite creation and redemption,
   active-org switching (including the "no longer a member" 403
   case). Use the existing `tests/test_auth.py` patterns. The
   test count target: ~30 new tests, bringing the suite to ~290.

9. **docs: org guide + OpenAPI snapshot update** — *S, P1*

   New `docs/orgs.md` (linked from `docs/self-host.md` and the
   README) explaining the user-vs-org scope, how to create an org,
   the role model, and the migration story (operators running
   0.6.0 get orgs on first 1.0.0 deploy with no manual step). The
   `docs/openapi.json` snapshot is regenerated via
   `task openapi-snapshot` and committed — the CI gate fails
   if this is forgotten, so the openapi-snapshot workflow is the
   enforcement.

**Slice 2 exit criteria:** all new endpoints are reachable and
return the documented responses; the OpenAPI snapshot test passes;
the web UI's org switcher switches active orgs and the
admin page renders the member list; `docs/orgs.md` is published;
the full test suite (259 + ~30 new = ~290) passes; ruff
format + ruff check + mypy are all green.

## Slice 3 — Stability freeze + 1.0.0 release cut

The third slice is the cutover. The data model from Slice 1 and
the org API/UI from Slice 2 have been live for at least one
release cycle (the cycle is 0.6.0 → 1.0.0, since this is the
*next* release after the API stability commitment), and the
0.6.0 OpenAPI spec has held for that cycle. This slice retires
the deprecation warnings that 0.6.0 introduced (the
`STANDUP_API_TOKEN` rename, per `docs/api-stability.md`'s
deprecation procedure), writes the 1.0.0 CHANGELOG entry, and
tags the release.

### Deprecation retirement

1. **security: drop `STANDUP_API_TOKEN` support** — *S, P1*

   The 0.6.0 release deprecated `STANDUP_API_TOKEN` in favour of
   `STANDUP_API_KEY` (one minor release ago). Per
   `docs/api-stability.md`'s deprecation procedure ("something
   deprecated in 0.6.0 goes no sooner than 0.8.0"), the
   deprecation must run for at least two minor releases before
   removal. 1.0.0 is the major version bump; the deprecation
   clock is satisfied if we also document the removal in the
   1.0.0 CHANGELOG. The removal is one line in
   `backend/cli_auth.py` (drop the `STANDUP_API_TOKEN` env var
   read) plus the corresponding test in `tests/test_cli_auth.py`.

   **Gotcha:** the deprecation period here is technically
   "0.6.0 → 0.8.0" (two minor releases), not "0.6.0 → 1.0.0"
   (one minor + one major). 1.0.0 is allowed to remove it
   because (a) the deprecation has been in place for at least
   the minimum window, and (b) major versions are explicitly
   allowed to break the API per SemVer. Document this explicitly
   in the CHANGELOG so downstream users know it's expected.

2. **API: remove the `legacy_token_alias` header from CLI responses** — *S, P1*

   The CLI's `--token` flag has accepted the 0.5.0 `STANDUP_API_TOKEN`
   value as an alias for `STANDUP_API_KEY` since 0.5.0 (per the
   0.6.0 plan). The alias is removed in Slice 3 — the CLI only
   reads `STANDUP_API_KEY`. The flag is unchanged; only the env
   var lookup is updated. The migration doc is updated to call
   this out.

### Release cut

3. **docs: 1.0.0 CHANGELOG entry + migration doc cross-link** — *S, P1*

   `CHANGELOG.md` gets `## [1.0.0] - <date>` with a 1-paragraph
   framing ("the multi-tenant release; data model gains orgs, the
   API surface stays stable, the stability promise from 0.6.0
   is the contract") plus the usual `### Added`, `### Changed`,
   `### Removed` headers. The Removed section names
   `STANDUP_API_TOKEN` explicitly. `docs/migrations/0.6.0-to-1.0.0.md`
   is referenced from the CHANGELOG entry.

4. **chore: bump `pyproject.toml` to 1.0.0, regen `uv.lock`, tag** — *S, P1*

   `version = "1.0.0"`, `uv lock` (no expected dep changes —
   the alembic migration is a code change, not a dep change),
   `git tag -a v1.0.0 -m "..."`, push the tag. Annotated tag —
   the message is the release notes summary.

5. **docs: archive `docs/1.0.0-plan.md` to `docs/releases/1.0.0-plan.md`** — *S, P2*

   Per the project's pattern (`docs/releases/0.5.0-plan.md`,
   `docs/releases/0.6.0-plan.md` are the prior archived plans).
   Done in a small follow-up PR after the release tag, so the
   archive commit doesn't pollute the 1.0.0 cut.

**Slice 3 exit criteria:** the 0.6.0 OpenAPI snapshot has held
for one release cycle (i.e. the only diff in `docs/openapi.json`
between 0.6.0 and 1.0.0 is the *additive* `/orgs/*` endpoints
from Slice 2 — no field renames, no status code changes, no
route removals); the deprecation procedure is retired per its
own terms; the CHANGELOG is updated; the `v1.0.0` tag is
pushed; the test suite is green.

After 1.0.0 the project will be:

- **Multi-tenant.** A user belongs to one or more orgs; every per-user
  resource (repos, prompt settings, shared summaries, API keys, audit
  log) is org-scoped. The data model is right; the API is right; the
  UI is right.
- **API-stable for real.** The 0.6.0 OpenAPI spec held for one release
  cycle. The deprecation procedure from `docs/api-stability.md` was
  used against us (the `STANDUP_API_TOKEN` retirement) and it worked.
- **Self-host only.** Operators continue to control user creation; no
  Stripe, no SaaS signup, no billing. The 1.0.0 release is the one a
  small team runs on a homelab box with confidence that the public
  surface is frozen.

The 1.1.0 release will be cut when OIDC lands. The auth backend
already has the extension point (`backend/auth.py:get_current_user` is
the natural swap site — the 0.5.0 plan called this out, the 0.6.0
plan reaffirmed it, and 1.0.0 leaves it intact). OIDC is the natural
follow-on: account linking, provider config UX, session-vs-token
semantics. The 1.0.0 release notes will name 1.1.0 as "OIDC + per-org
provider keys + teams (if requested)." The project does not need
another API stability commitment to add OIDC — the procedure is in
place, the snapshot test is in place, and a new minor release can
land it on top of the frozen 1.0.0 surface.
