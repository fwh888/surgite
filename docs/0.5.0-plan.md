# 0.5.0 Plan

Targeted at **v0.5.0** — the **auth + multi-user** release.

Builds on the 0.4.0 baseline, which shipped the foundation slice (background
ingest scheduler, structured logging, per-IP rate limit, backup/restore,
streaming summaries) and the user-facing slice (shareable links, per-repo
prompts, CLI↔API bridge, deep health). 0.4.0 is the last release where
standup-gen is a single-tenant, no-auth app intended to run on a trusted
network. 0.5.0 picks up the work that's required to make it safe to expose
to people who aren't the operator: real authentication, per-user data
isolation, and the self-hosting ergonomics an external user expects
(0.4.0 was the last release with a "no users, no auth" model in mind; 0.5.0
ships that model and 0.6.0+ builds the multi-tenant features on top).

This release is **allowed to break the 0.4.0 API and CLI** (pre-1.0.0, no
deprecation cycle required). 0.5.0 is the cutover: anyone running 0.4.0
needs to be ready to migrate, and the migration path is documented in
`docs/migrations/0.4.0-to-0.5.0.md` (added in slice 1).

The plan is organised by theme rather than by file, with each item carrying
an effort estimate (**S** ≤ half a day, **M** = 1–2 days, **L** = 3+ days)
and a priority (**P1** = blocking for the release / blocking for 1.0.0,
**P2** = should land in 0.5.0, **P3** = nice-to-have, defer to 0.5.1 or
0.6.0 if needed).

Estimated total: **~18–24 dev days**, deliberately larger than 0.4.0's
foundation+user-facing pair because the auth and data-isolation work
touches every API route and most of the data model. 0.5.0 is sized as
**three PRs** (foundation → security → multi-user) rather than 0.4.0's
two, and assumes a calm week per PR.

---

## Out of scope (explicitly deferred)

These are 0.6.0+ candidates that would be tempting to fold in here but
shouldn't be. Listing them now so we don't get scope-crept.

- **SSO / OIDC integration** (Google, GitHub, GitLab, generic OIDC). The
  0.5.0 auth model is **email + password with first-party session cookies**
  — that's enough to be safe to expose, and enough to land all the
  per-user data-isolation work. OIDC providers are a 0.6.0 feature and
  have their own UX problems (account linking, org mapping) that we
  shouldn't be solving while auth itself is still new. The auth backend
  is designed to be extended with OIDC later (see item #6) but no
  provider is wired up in 0.5.0.
- **Organisations / teams / billing.** 0.5.0 models users and per-user
  data, not orgs. Orgs require their own data model, their own invite
  flow, and a billing story. Defer.
- **Background-job framework swap** (RQ, Celery, Arq). The lifespan
  scheduler is fine for the current load; if 0.6.0 needs to schedule
  long-running jobs across processes we'll revisit.
- **A web-based user-invite flow.** Invites for 0.5.0 happen via an
  admin issuing an invite token out of band (CLI or `POST /admin/invites`).
  A polished "send an email" flow is 0.6.0.
- **PWA / mobile UI / push notifications.** Web UI stays as-is.

## Slice 1 — Foundation: data model + auth primitives (PR #53)

The first slice makes the codebase auth-aware without yet enabling
authentication end-to-end. The goal is to land the schema, the crypto
helpers, the password-handling primitives, and the "current user"
dependency in a way that doesn't break any 0.4.0 behaviour. After this
PR, the API still allows anonymous access — that's intentional, gated
on an `AUTH_MODE=off` env var that's the default for the duration of
the slice.

### Data model

1. **`users` table** — *M, P1*
   `id` (uuid), `email` (citext, unique, lower-cased), `password_hash`
   (argon2id via `argon2-cffi`, parameters tuned for ~250 ms on the
   target server), `display_name`, `is_active` (bool, default true —
   no email verification in 0.5.0, see below), `is_admin` (bool, default
   false), `created_at`, `last_login_at` (nullable). The `email` column
   is `citext` so case-insensitive lookups are index-supported; the
   unique constraint enforces it.
2. **`sessions` table** — *S, P1*
   `id` (random 256-bit string, base64url-encoded as the cookie value),
   `user_id` (FK → users, cascade delete), `created_at`, `expires_at`,
   `last_seen_at`, `user_agent` (truncated, nullable), `ip` (truncated
   to /24 or /64, nullable). Sessions are server-side records; the
   cookie carries the opaque session id, not user data.
3. **`invites` table** — *S, P1*
   `id` (uuid), `token` (random, single-use), `email` (nullable — null
   means "any email can claim this invite"), `role` (text — `'user'` or
   `'admin'`), `created_by` (FK → users), `created_at`, `expires_at`,
   `used_at` (nullable), `used_by` (FK → users, nullable). Bootstrap
   path: first run creates an `is_admin=True` invite that the operator
   redeems via the CLI, then issues more invites from there.
4. **Per-user data partitioning** — *M, P1*
   Every existing table (`repos`, `commits`, `prompt_settings`,
   `shared_summaries`) gains a non-nullable `owner_id` FK → `users`. A
   migration backfills from a configurable "default owner" (a CLI
   argument to `alembic upgrade head`, or a `BOOTSTRAP_OWNER_EMAIL`
   env var the operator sets on first run). All queries gain an
   `owner_id = :current_user` predicate. This is the biggest single
   change in the release — touches every endpoint — and the migration
   is the most likely place to break a self-hoster's upgrade, so it
   gets a dedicated `docs/migrations/0.4.0-to-0.5.0.md` (see #5).
5. **Migration guide + upgrade path** — *M, P1*
   `docs/migrations/0.4.0-to-0.5.0.md` documents the three upgrade
   paths:
     - **Greenfield (most external users):** `docker compose down`,
       pull 0.5.0, `BOOTSTRAP_OWNER_EMAIL=me@example.com docker compose
       up -d`, the app creates that user with an `is_admin=True`
       invite, the operator redeems it via `standup --redeem-invite`,
       and they're in.
     - **Single-operator upgrade (current 0.4.0 self-hosters):** same as
       greenfield plus a `migrate-0.4-owner.sh` script that takes the
       existing Postgres database, prompts for a bootstrap email +
       password, creates the user, and re-associates every existing
       repo / commit / prompt_settings / shared_summary row with that
       user.
     - **Hosted-as-multi-tenant (future):** not supported in 0.5.0.
   The migration runs `CREATE INDEX CONCURRENTLY` on the new FKs
   against a reasonably-sized dataset; for large datasets a separate
   "pre-migration index" step is documented.

### Auth primitives

6. **`backend/auth.py` — password hashing, session creation, `get_current_user` dependency** — *M, P1*
   Module boundaries:
     - `hash_password(plain) -> str` and `verify_password(plain, hash) -> bool`
       wrapping `argon2-cffi`.
     - `create_session(user_id, *, ip, user_agent) -> Session` and
       `revoke_session(session_id) -> None`.
     - `purge_expired_sessions() -> int` — called by the lifespan
       scheduler alongside `_ingest_all_repos` (every
       `SESSION_CLEANUP_INTERVAL` seconds, default 1 h).
     - `get_current_user(request: Request, response: Response) -> User`
       FastAPI dependency — reads the `__Host-standup_session` cookie,
       looks up the session, returns the user. Sets a new cookie if
       `expires_at - now() < SESSION_REFRESH_THRESHOLD` (sliding
       sessions). Three modes selected by `AUTH_MODE`:
         - `off` — returns a singleton "anonymous" user (so the rest of
           the code can assume a `current_user` always exists), every
           existing repo / commit is owned by `BOOTSTRAP_OWNER_EMAIL`'s
           user. This is the 0.4.0 behaviour.
         - `single_user` — every request resolves to the bootstrap
           user, no login UI, no `/login` route exposed. The auth
           machinery exists and is tested; the only thing disabled
           is the login flow. The right mode for "I just want auth on
           the API" deployments and for testing.
         - `multi_user` — full session-cookie auth, `/login` and
           `/logout` routes, every request resolves to a real user.
           This is the mode external users actually want.
     - The dependency is wired into the API surface but **returns
       401 only when `AUTH_MODE != "off"`**; in `off` mode it's a
       no-op so the existing 0.4.0 test suite still passes.
   Designed so OIDC can be added later by replacing only
   `get_current_user` with a version that consults an OIDC verifier
   first, falling back to the cookie.
7. **Session cookie hardening** — *S, P1*
   `__Host-` prefix, `Secure`, `HttpOnly`, `SameSite=Lax`. `Secure`
   requires HTTPS; in development the cookie is set with `Secure=False`
   only when `DEBUG=true`. Documented in the migration guide that
   running standup-gen over plain HTTP is no longer supported — the
   app will refuse to start in `multi_user` mode without TLS. (Traefik
   + step-ca in production; Caddy / `caddy trust` for local dev, or
   `mkcert`. The README grows a "local HTTPS" subsection.)
8. **`backend/cli_auth.py` — `standup login`, `standup logout`,
   `standup --redeem-invite`** — *M, P1*
   The CLI is the bootstrap path. `standup --redeem-invite <token>`
   hits `POST /auth/redeem-invite` (no auth required for invite
   redemption), sets a session cookie in a local cookie jar, and
   subsequent `standup --registered <name>` calls reuse it.
   `standup login` and `standup logout` are the interactive variants
   for an operator who wants to switch users. The CLI's existing
   `STANDUP_API_TOKEN` env var is **renamed to `STANDUP_API_KEY`**
   and re-purposed to a long-lived API key (see slice 2) — backward
   compat shim: if `STANDUP_API_TOKEN` is set, the CLI uses it as an
   API key and logs a one-time deprecation warning.

### Operational

9. **`scripts/upgrade-from-0.4.sh`** — *S, P1*
   One-shot script: pulls the existing Postgres password, runs the
   migration with the operator's chosen `BOOTSTRAP_OWNER_EMAIL`,
   re-keys any backup artifacts whose paths changed. Invoked manually
   by the operator; the docker-compose `db` container's entrypoint
   refuses to start against a 0.4.0 schema without it.
10. **`/health` and `/health/deep` no longer leak repo names** — *S, P1*
    0.4.0's `git ls-remote` probe picks an arbitrary repo from the DB;
    in `multi_user` mode that would leak repo existence to anyone
    hitting `/health`. Constrain the probe to repos the requesting
    user owns, and return a redacted `{ "components": { ... } }` shape
    that doesn't name specific repos in the response.
11. **`/providers` requires auth in `multi_user` mode** — *S, P1*
    0.4.0's `/providers` endpoint returns whether each provider has a
    key configured — that's an information disclosure if the app is
    exposed. In `multi_user` mode it requires `is_admin=True` and
    returns per-user provider status (each user configures their own
    provider keys; see slice 3). In `single_user` mode it's
    open as before.

**Slice 1 exit criteria:** All 11 items merged. `AUTH_MODE=*** is
indistinguishable from 0.4.0 behaviour. The full test suite passes
under all three auth modes. A greenfield install works end-to-end
via `standup --redeem-invite`. A 0.4.0 → 0.5.0 upgrade on a
single-operator deployment works via `scripts/upgrade-from-0.4.sh`.

## Slice 2 — Security: route protection, API keys, rate limits, secrets (PR #54)

The second slice turns on the auth machinery. After this PR,
`AUTH_MODE=multi_user` is the default and the API refuses to start
in any mode that doesn't terminate TLS. The goal is "safe to expose
to the public internet" — auth, transport security, abuse prevention,
and the operational signals to notice when something goes wrong.

### API surface

13. **All routes return 401 without a valid session in `multi_user`
    mode** — *M, P1*
    `/health`, `/health/deep`, `/login`, `/logout`, `/auth/*`,
    `/static/*`, and `/s/{slug}` are the only unauthenticated
    routes. Everything else — `/repos`, `/commits`, `/summary`,
    `/summary/stream`, `/summaries`, `/settings/prompt`,
    `/providers` — requires a session. The `current_user` dependency
    is the only gate; we don't sprinkle `Depends(...)` through every
    route handler (that's what the dependency is for).
14. **Per-user API keys for the CLI** — *M, P1*
    `POST /auth/api-keys` issues a new long-lived API key, returns it
    **once** in the response, and stores an argon2id hash of it. The
    CLI uses `Authorization: Bearer <key>` to authenticate. Keys
    have a `name` (so the user can revoke "laptop" without revoking
    "CI"), an optional `expires_at`, and a `last_used_at` for audit.
    `GET /auth/api-keys` lists keys (hashed value never returned);
    `DELETE /auth/api-keys/{id}` revokes. Standup-gen keeps a
    per-user rate limit on key issuance (default 10 / day, configurable).
15. **CSRF protection on state-changing requests** — *M, P1*
    The `__Host-` cookie is `SameSite=Lax` so the browser won't
    send it on cross-site POSTs, but defence in depth: state-changing
    requests (anything not `GET`/`HEAD`/`OPTIONS`) require a
    `X-Requested-With: standup-web` header from the SPA, and the
    server rejects anything that doesn't match. Cheap, no token
    rotation, doesn't break the CLI (which uses Bearer auth, not
    cookies). Documented in `docs/security.md`.
16. **Repo add path requires `is_admin` or an explicit
    `repos:create` capability** — *S, P1*
    In a multi-user deployment you usually want most users to *read*
    but only some users to *add* repos (which clones the repo into
    the API's filesystem and runs `git log` over it — a code
    execution surface if the URL is attacker-controlled). Default:
    every authenticated user can add a repo, but admins can flip a
    `REPO_ADD_GLOBAL_ONLY=true` env var to gate it to admins only.
    Both modes are tested.

### Abuse prevention

17. **Per-user rate limits, replacing the per-IP one** — *M, P1*
    The 0.4.0 rate limit is per-IP, which is wrong for a multi-user
    deployment (one user's burst throttles everyone behind the same
    NAT, and per-IP is useless behind a shared proxy). Replace with
    per-user limits on `/summary?ai=true` and `/summary/stream` (same
    5 / 60 s default), and a separate per-user limit on `/auth/login`
    (10 / 5 min — the lockout story, see #18). Per-IP limits stay as
    a *coarse* outer guard (e.g. 100 / min per IP across all users)
    to catch the "new user, fresh signup, spam" case.
18. **Account lockout on failed logins** — *S, P1*
    10 consecutive failures within 15 min → 15 min lockout, per
    `(email, ip)`. `users` gains a `failed_login_count` and
    `locked_until`. Admins can unlock via `POST /admin/users/{id}/unlock`.
    The lockout is logged at `WARNING` with the email and a
    truncated IP.
19. **Shareable links are user-scoped** — *M, P1*
    0.4.0's `shared_summaries` rows are global — any user with a
    slug can read the summary. In 0.5.0 the row carries `owner_id`,
    `GET /summaries/{slug}` checks ownership, and `GET /s/{slug}`
    continues to work but only for shares created by the requesting
    user. Cross-user share access is a 404 (not 403, to avoid
    leaking slug existence). Default `SHARE_TTL_DAYS` drops from
    7 to 14 (longer is fine when shares are scoped) but stays
    configurable.

### Secrets

20. **Per-user provider keys in the database, not env vars** — *L, P1*
    0.4.0 reads `ANTHROPIC_API_KEY` etc. from the environment. In
    `multi_user` mode each user configures their own provider keys
    via `PUT /settings/provider-keys` (returns `{ "configured": true }`,
    never the key material). Keys are encrypted at rest with
    Fernet (`cryptography`), the master key derived from a
    `SECRETS_ENCRYPTION_KEY` env var. The summarizer looks up keys
    by `current_user.id`, falling back to the global env-var key in
    `single_user` mode. `/providers` returns per-user status. New
    `provider_keys` table:
    `id`, `user_id` (FK), `provider` (text), `encrypted_key`,
    `created_at`, `revoked_at` (nullable). The CLI's
    `--provider anthropic` continues to read from env in
    `single_user` mode; in `multi_user` mode it requires a
    pre-configured user with that provider set.
21. **Secret rotation tooling** — *S, P2*
    `scripts/rotate-secrets.sh` rotates the
    `SECRETS_ENCRYPTION_KEY` in place: re-encrypts every
    `provider_keys` row under the new key, updates the running
    process via SIGHUP (the app reloads the env var on signal).
    Tested against a 100-key dataset. The `SECRETS_ENCRYPTION_KEY`
    is generated by the app on first run if not set and saved to
    `.secrets_key` with `chmod 600`; the operator is told to back
    it up.

### Observability

22. **Audit log table + `GET /admin/audit`** — *M, P2*
    `audit_log` table: `id`, `actor_id` (FK → users, nullable for
    pre-auth events like login failures), `action` (text, e.g.
    `repo.create`, `auth.login.success`, `auth.login.fail`,
    `provider_key.create`), `target_type` (text, nullable),
    `target_id` (text, nullable), `ip` (truncated), `user_agent`
    (truncated), `metadata` (jsonb), `created_at`. Indexes on
    `actor_id`, `created_at`, `action`. `GET /admin/audit?since=…`
    is admin-only and paginated. The structured logger gets an
    `audit` namespace that writes to both the audit table and the
    standard log stream, so log shippers see the same events.

**Slice 2 exit criteria:** All 10 items merged. A fresh
`AUTH_MODE=multi_user` install with two users (one admin) is safe
to put on the public internet behind Traefik with a step-ca cert.
The full test suite passes. The 0.4.0 → 0.5.0 upgrade path is
documented and tested. A threat-model document (`docs/security.md`)
covers the rate limits, lockout, CSRF, and share-scoping choices.

## Slice 3 — Multi-user features: per-user UX, invites, polish (PR #55)

The third slice is the user-visible payoff. After this PR, multi-user
deployments feel native: signup via invite, per-user repos, per-user
summaries, per-user prompts, per-user provider keys (already
landed in slice 2, UI lands here). The data-isolation plumbing
landed in slice 1; the security controls landed in slice 2; this
slice is the ergonomics.

### Signup & user management

23. **`/signup` (invite-gated) and `/login` routes + UI** — *M, P1*
    `/signup?token=…` lets an invited user create their account.
    `/login` is the email + password form. Both routes are
    public. The login form is unstyled HTML (no framework, no JS)
    so it's small and works without the SPA. CSRF is enforced
    on the form POST (the cookie + `X-Requested-With` story
    from #15 is the only line of defence we need; we don't add
    a separate CSRF token). Failed logins get the
    "try again in N minutes" message from #18; successful logins
    set the session cookie and redirect to `/`.
24. **Admin UI for user management** — *M, P2*
    `/admin/users` (admin-only): list users, see last login, see
    failed-login count, see locked-until, click "unlock" or
    "deactivate". "Invite user" button creates an invite, copies
    the redeem URL to the clipboard (or, in 0.5.0, displays it for
    the admin to send out of band; the email story is 0.6.0).
25. **Password change + reset** — *M, P2*
    `PUT /auth/password` (authenticated) for the
    authenticated-user case. `POST /auth/password-reset` and
    `POST /auth/password-reset/confirm` (public) for the
    forgotten-password case. The reset token is emailed — wait,
    there's no email. 0.5.0's password reset is admin-mediated:
    `POST /admin/users/{id}/reset-password` returns a one-time
    reset token the admin delivers out of band. The token grants
    no access on its own; it sets a new password and locks the
    user out of all active sessions. Real email-delivered reset
    is 0.6.0 when there's a mail provider.

### Per-user UX

26. **Frontend: per-user repo list, per-user prompt settings,
    per-user summary history** — *L, P1*
    The 0.4.0 SPA assumed a single user; the `data-theme` selector
    in the top bar gains a "logged in as <name>" indicator with a
    logout button. The repos page filters to the current user's
    repos (the API already does this; the UI is updated to
    reflect it). The summary history page shows the current
    user's prior summaries, with a "shared by" link to summaries
    *they* shared and a "shared with me" tab (empty in 0.5.0
    since cross-user share isn't a thing yet — that page exists
    for the 0.6.0 feature). The prompt settings panel is scoped
    to the current user; per-repo prompts stay (they're already
    per-user in slice 1).
27. **Frontend: login / signup / invite-redeem pages** — *M, P1*
    Minimal terminal-aesthetic pages (the 0.2.0 design language):
    `/login`, `/signup?token=…`, `/password-reset`. The login page
    is the first thing an unauthenticated user sees when they hit
    any non-public route — a small client-side redirect at the
    root of the SPA. (The FastAPI `get_current_user` dependency
    also returns 401 for API calls; the UI just handles that by
    redirecting to `/login`.)
28. **CLI: `standup login` and `standup logout` interactive flows** — *S, P2*
    `standup login` prompts for the API URL, email, and password
    (or reads them from env), authenticates, and saves the session
    cookie in `~/.config/standup/session` (Linux) /
    `~/Library/Application Support/standup/session` (macOS). Keyring
    integration is **deferred to 0.6.0** — 0.5.0 stores the cookie
    in a 0600-mode file. `standup logout` deletes the cookie. The
    existing `STANDUP_API_URL` and `STANDUP_API_KEY` env vars are
    unchanged in behaviour.

### Polish

29. **`docs/self-host.md`** — *M, P1*
    End-to-end self-hosting guide. Covers:
      - Hardware sizing (this is a small app — 1 vCPU, 512 MB RAM,
        2 GB disk for a small team; we say so).
      - docker-compose quickstart (the existing one, updated for
        the bootstrap flow).
      - `BOOTSTRAP_OWNER_EMAIL` / invite redemption walkthrough.
      - TLS: Traefik + step-ca (homelab-style) and Caddy + Let's
        Encrypt (external-style) and `caddy trust` (local dev).
      - Backup / restore (the 0.4.0 scripts, updated for the new
        `provider_keys` and `audit_log` tables).
      - Upgrade: the 0.4.0 → 0.5.0 migration step-by-step.
      - The threat model (`docs/security.md`, see slice 2) in
        summary form.
      - Operational runbook: how to revoke all sessions, how to
        rotate the secrets key, how to read the audit log.
    This doc is the single biggest user-experience win in 0.5.0
    for external users; it's the doc that makes "I can run this
    for my team" actually true.
30. **README rewrite** — *S, P1*
    Lead with the self-host story, not the CLI story. Add a
    "screenshots" / "demo GIF" placeholder (one TODO) for
    0.5.1. Keep the dev quickstart below the fold. The badge
    row is updated to include a "build passing" badge (already
    there) and a "license" badge (already there) and adds a
    "self-hostable" badge.
31. **`CHANGELOG.md` [Unreleased] intro rewritten for the
    1.0.0 story** — *S, P2*
    The current `[Unreleased]` block still says "rework on the
    way to a 1.0.0 release", which is now an actionable claim.
    Rewritten to: "0.5.0 is the auth + multi-user release. After
    0.5.0, the remaining work for 1.0.0 is multi-tenant features
    (orgs, billing, SSO) and the API stability promise. The
    1.0.0 release will be cut when 0.6.0 and 0.7.0 (or whichever
    follows) close out the multi-tenant and stability work."

**Slice 3 exit criteria:** All 9 items merged. A two-user
deployment (one admin, one regular user) works end-to-end: admin
signs up via bootstrap, invites the second user, second user
redeems, each user sees only their own data, each can configure
their own provider keys, the docs are complete and accurate.

After 0.5.0 the project will be:

- **Auth-first.** No more "this is for trusted networks" assumptions.
- **Multi-user.** The data model and the API surface both treat
  users as first-class.
- **Self-hostable for real.** The docs and the deployment story
  match the actual capabilities of the app.
- **One step from 1.0.0.** The remaining work is multi-tenant
  features and the API stability promise — both well-scoped,
  neither requiring an auth rewrite.

The 1.0.0 release will be cut when those remaining items land
(0.6.0+ scope, to be planned after this release ships).
