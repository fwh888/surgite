# 0.6.0 Plan

Targeted at **v0.6.0** — the **API stability + keyring + email** release.

Builds on the 0.5.0 baseline, which shipped the auth + multi-user work
(`AUTH_MODE` plumbing, per-user data isolation, sessions, invites, audit
log, Fernet-encrypted provider keys, the self-host guide). 0.5.0 made the
project safe to expose to external users. (The historical 0.5.0 plan
is archived at `docs/releases/0.5.0-plan.md`; the current roadmap is
this document.) 0.6.0 makes the contract with
those users explicit: a published, snapshot-tested OpenAPI surface, a
deprecation procedure, and a security backport commitment. The 1.0.0
release will be cut when orgs and OIDC land on top of a stable contract
— both well-scoped, both needing 0.6.0 to be done first.

This release is **allowed to break the 0.5.0 API and CLI** in minor ways
(rename a header, add a field, change a default). It is **not** allowed
to remove a route, change a status code, or rename a JSON field without
going through the deprecation procedure introduced in this release —
because the moment we ship 0.6.0, that procedure applies to *us* as well
as to downstream.

The plan is organised by theme rather than by file, with each item
carrying an effort estimate (**S** ≤ half a day, **M** = 1–2 days, **L**
= 3+ days) and a priority (**P1** = blocking for the release, **P2** =
should land in 0.6.0, **P3** = nice-to-have, defer to 0.6.1 or 0.7.0 if
needed).

Estimated total: **~10–15 dev days** across **three slices** (snapshot
plumbing → stability docs & policy → keyring + email). The slice
count mirrors 0.5.0's three-PR cadence.

## Out of scope (explicitly deferred)

These are 1.0.0+ candidates that would be tempting to fold in here but
shouldn't be. Listing them now so we don't get scope-crept.

- **Organisations / teams / billing.** 1.0.0 scope. The org model
  touches the data model (every existing table gains `org_id` and
  `owner_id` becomes optional / removed for shared resources), the API
  surface (new `/orgs/*` routes, RBAC), and the auth model (org
  membership, org-scoped invites). None of that should ship while the
  API stability contract is still soft. Once 0.6.0's snapshot test is
  green, we can layer orgs on top of a frozen surface.
- **OIDC / SSO** (Google, GitHub, GitLab, generic OIDC). 1.0.0 scope.
  The 0.5.0 plan already designed the auth backend so OIDC slots in
  by replacing `get_current_user` with an OIDC-verifier-first version
  falling back to the cookie. That's still the right extension point.
  Account linking, provider config UX, and session-vs-token semantics
  are enough work to be a real PR — not a polish item.
- **Multi-region / horizontal scale.** Postgres read replicas, Redis
  for sessions, etc. Currently single-instance. The org model is what
  triggers the move to multi-region for real users; not before.
- **PWA / mobile UI / push notifications.** Web UI stays as-is.
- **Demo GIF compression.** The 0.5.1 follow-up noted the demo GIF is
  2.8 MB and a `gifsicle -O3 --lossy=80` pass would cut it in half.
  Tiny polish, not a 0.6.0 item.

## Slice 1 — OpenAPI snapshot plumbing (PR #91)

The first slice builds the *mechanical* part of the stability
commitment: a way to generate a canonical OpenAPI document from the
running app, a way to detect when it changes, and a CI gate that fails
PRs which change the surface unintentionally. After this PR, "did you
break the API?" is a CI question, not a review question.

The slice does *not* write the stability policy, the deprecation
procedure, or the security backport SLA — those are docs and decisions,
not code, and they belong in slice 2 where the policy framing is the
whole point. This slice is plumbing only.

### Snapshot generation

1. **Generate a canonical OpenAPI document from the FastAPI app.**
   *S, P1.* A `scripts/dump_openapi.py` script that imports
   `backend.api:app`, calls `app.openapi()`, and writes the result to
   `docs/openapi.json`. The output is normalised (sorted keys, no
   whitespace) so diffs are clean. Run it on a fresh `uv sync` against
   the current main, commit the result. The committed file is the
   baseline.

2. **CI workflow: regenerate the snapshot and fail on diff.**
   *S, P1.* A new `.forgejo/workflows/openapi-snapshot.yml` (matching
   the existing workflow style) that:
     1. Sets up Python 3.14 + `uv sync`.
     2. Runs `uv run python scripts/dump_openapi.py > /tmp/openapi.json`.
     3. Diffs against `docs/openapi.json`.
     4. Fails the workflow with a clear message ("API surface changed;
        update the snapshot with `make openapi-snapshot` and review
        the diff") if the files differ.

   The workflow runs on every PR. It's a hard gate, not advisory.

3. **`make openapi-snapshot` target + pre-commit hook.**
   *S, P1.* A `Makefile` (or `scripts/update_snapshot.sh`, whatever
   style matches the existing repo — there isn't one, so pick the
   leaner option) that runs the dump and copies the result to
   `docs/openapi.json`. Document the workflow in `docs/CONTRIBUTING.md`
   or extend the existing AGENTS.md commands section: "if you change a
   route, run `make openapi-snapshot` and commit the result, and
   explain the change in the PR description."

4. **Diff-friendly schema config.**
   *S, P1.* Configure FastAPI's OpenAPI generator to produce stable
   output: explicit `operation_id`s on every route, sorted enum
   members, no Python `repr` leakage in descriptions. The
   `dump_openapi.py` script enforces this on its end too
   (`json.dumps(..., sort_keys=True, indent=2, separators=(",", ": "))`
   with a fixed key-ordering pass). Goal: a one-line route addition
   shows up as a ~10-line diff in `docs/openapi.json`, not a 200-line
   re-sort.

### Coverage

5. **Every route has an OpenAPI summary, description, and tag.**
   *S, P2.* The 0.5.0 routes were added fast (slice 1, 2, 3 each
   shipped ~10 routes in a week). Some have terse or missing
   `summary=` / `description=` / `tags=` kwargs. Audit all routes in
   `backend/api.py`, fill in the gaps. Output goal: the generated
   OpenAPI document is readable as a reference, not a wall of
   `endpoint_path_get`.

6. **Document the error response shapes.**
   *S, P2.* Add `responses={404: {"model": ErrorResponse}, ...}` to
   every route that can fail. The 0.5.0 plan promised a stable error
   shape (`{"error": "message"}`); this is the code change to make
   that promise true. Small models in `backend/schemas.py` for each
   documented error (or one shared `ErrorResponse` model with a
   `code` field — pick the leaner option). The snapshot test
   verifies the response docs are present.

### Housekeeping

7. **The plan's other promises, retroactively documented.**
   *S, P1.* 0.5.0 promised a stable error shape, a stable
   `/health/deep` shape, and per-user rate-limit headers. The shapes
   exist in code; they're just not declared on the routes. This
   slice's coverage work (#5, #6) is the right place to land the
   declarations. If a promise turns out to have been *imprecise* (the
   actual shape differs from the plan's intent), this is the slice
   to fix it — *before* the snapshot locks it in.

**Slice 1 exit criteria:** All 7 items merged. The
`openapi-snapshot` CI workflow is green on main. The committed
`docs/openapi.json` matches the live app. A deliberately-breaking
change to a route (added in a throwaway branch) fails the CI
workflow with a clear message. The OpenAPI document is
self-explanatory to a developer who has never read the source.

## Slice 2 — Stability policy, deprecation procedure, and the
security backport commitment (PR #92)

The second slice turns the mechanical snapshot into a *contract*. After
this PR, the project has a written stability policy (what we promise
not to break), a deprecation procedure (how we phase out something
when we have to), a security backport SLA (how long we'll patch old
versions), and a public changelog format that makes all three of those
things checkable.

The slice is mostly docs. It includes one small code change (#9: the
deprecation markers) and one small CI change (#10: the deprecation
gate). Everything else is policy, examples, and link-rot fixes.

### Stability policy

8. **`docs/api-stability.md` — the public stability policy.**
   *M, P1.* The headline document for 0.6.0. Covers:
     - **What we promise not to break** in a minor release: route
       paths, HTTP methods, request/response JSON shapes (top-level
       keys, types), status codes, header semantics, error envelope
       shape. New fields are additive; existing fields don't change
       type. Removing a route or field requires a deprecation cycle
       (see #9).
     - **What we explicitly reserve the right to break** in a minor
       release: default values, deprecation timelines, internal
       IDs, log formats, undocumented `x-` headers, anything in
       `/health/deep` that's marked as "informational only."
     - **What we promise for major releases (1.0.0+):** a 6-month
       overlap window where the previous major is still supported for
       security patches, with a written migration guide.
     - **What we promise never:** no surprise field removals in
       patches; no undocumented behaviour; no silent semver.

   The tone matches `docs/security.md` and `docs/self-host.md` —
   clear, direct, no marketing. Two pages, not twenty.

9. **Deprecation markers in code + the deprecation gate.**
   *M, P1.* When a route or field has to change, the change goes
   through a deprecation cycle:
     1. Mark the route or field as deprecated in the OpenAPI
        document (FastAPI's `deprecated=True` kwarg on the route;
        Pydantic's `Field(..., deprecated=True)` on the model).
     2. Return a `Deprecation` response header with the date the
        marker was added and the planned removal version.
     3. Log a `WARNING` on every deprecated-path hit (so the
        operator sees traffic moving off).
     4. The route / field stays for at least one minor release
        before removal. (Additive: a route marked deprecated in
        0.6.0 can be removed in 0.8.0 at the earliest.)

   A `scripts/check_deprecations.py` script + CI workflow
   (`.forgejo/workflows/deprecation-audit.yml`) that runs nightly
   on main and fails if any route / field has been marked
   deprecated for more than two minor releases without removal or
   re-stabilisation. This is the *operational* counterpart to
   #8's *policy* statement.

10. **Public changelog format with a deprecation section.**
    *S, P1.* Extend the existing `CHANGELOG.md` Keep-a-Changelog
    structure with a `### Deprecated` subsection under each release
    (next to `### Added` / `### Changed` / `### Removed`). The
    section is empty for releases with no deprecations. The first
    entry under this section reads:

    > Routes / fields marked deprecated in this release will be
    > removed no earlier than the next minor release after the
    > one that follows. See `docs/api-stability.md` for the full
    > policy.

    This makes the deprecation contract *checkable* — anyone can
    read the last three changelogs and know what's going away.

### Security backport commitment

11. **`docs/security-support.md` — supported versions and the SLA.**
    *S, P1.* A small doc that says:
      - Which versions get security patches.
      - For how long after release (default: latest minor + previous
        minor for 6 months after the next minor ships).
      - How to report a vulnerability (the existing
        `docs/security.md` threat model has a "Reporting" section —
        this doc links to it and adds the response-time commitment:
        acknowledge within 2 business days, triage within 5,
        patch in the next supported release or sooner if severity
        warrants an out-of-cycle release).
      - The CVE / GHSA process (or whatever the project will
        actually use — pick one and document it; the lean choice
        is "we publish advisories in the GitHub-style / Forgejo
        security advisory format, no CVE assignment for low-severity
        issues").

### Documentation hygiene

12. **The link-rot sweep the 0.5.0 plan flagged.**
    *S, P2.* The 0.5.0 plan's #12 mentioned "AGENTS.md / CHANGELOG
    link rot" — it landed for the 0.5.0 → 0.6.0 transition but
    only partially. The 0.6.0 plan adds three new docs
    (`api-stability.md`, `security-support.md`, the OpenAPI
    snapshot). Update the README's docs index, the `docs/README.md`
    table of contents (if one exists; if not, the README's doc
    list), and the AGENTS.md commands section to reference them.

13. **The deprecation procedure applied to the 0.5.0 leftover.**
    *S, P2.* A 0.5.0 → 0.6.0 entry in the `CHANGELOG.md`
    `### Deprecated` section noting that the renamed
    `STANDUP_API_TOKEN` env var (now an alias for
    `STANDUP_API_KEY`, with a deprecation warning logged once per
    session) is scheduled for removal in 0.8.0. This is the first
    real use of the new procedure — we eat our own cooking.

    Also: audit any other 0.5.0 changes for things that should
    have gone through the procedure but didn't. The 0.5.0 plan
    explicitly said pre-1.0.0 doesn't require a deprecation
    cycle, so this audit is informational — the only mandatory
    deprecation in 0.6.0 is the `STANDUP_API_TOKEN` rename
    formalisation.

**Slice 2 exit criteria:** All 6 items merged. `docs/api-stability.md`
and `docs/security-support.md` are linked from the README. The
deprecation gate is green (no routes currently over-aged). The
CHANGELOG's `### Deprecated` section is present and has the
0.5.0 → 0.6.0 entry. A downstream user reading only the public
docs (README, api-stability, security-support) can answer: "what
will you break, when, and how will I know?"

## Slice 3 — Keyring + email-delivered password reset (PR #93)

The third slice closes out the lightweight items the 0.5.0 plan
deferred. After this PR, the CLI's session cookie lives in the
OS keyring (not a 0600 file), password reset works over email
(not admin-mediated), and the `### Deprecated` section in the
CHANGELOG has its first real entry that's not the
`STANDUP_API_TOKEN` rename.

This slice is the "earnest" deliverable — it's the one that
makes the product noticeably nicer to use for a real team. Slice
1 was a CI workflow; slice 2 was a policy doc; this one is code
that does something.

### CLI keyring integration

14. **Replace the 0600 session file with an OS-keyring entry.**
   *M, P1.* The 0.5.0 plan deferred keyring integration with the
   note: "0.5.0 stores the cookie in a 0600-mode file, which is
   good enough for headless servers and CI runners." 0.6.0 is
   the time to do it right. The new behaviour:
     - On macOS: `keyring` library uses the login keychain.
     - On Linux: `keyring` library uses the Secret Service (GNOME
       Keyring, KWallet, KeePassXC — whatever the user has
       configured). Fall back to the 0600 file if the Secret
       Service is unavailable (headless CI, no D-Bus).
     - On Windows: `keyring` uses the Credential Manager.
     - The CLI's `--keyring-file` flag forces the 0600 file
       fallback for testing and headless servers.
   `keyring` is the only new dependency. It pulls in
   `SecretStorage` on Linux, which is a PyPI dep but uses the
   user's existing D-Bus — no daemon to ship.

15. **Keyring migration: read from the 0600 file, write to keyring.**
   *S, P1.* On first run after upgrading, if the 0600 session
   file exists, read it, write it to the keyring, delete the file
   with `shred`-style semantics (overwrite, then unlink), and log
   the migration. The migration is a no-op on a clean install.

16. **Document the keyring behaviour in the self-host guide.**
   *S, P2.* `docs/self-host.md` grows a "CLI session storage"
   section explaining: where the cookie lives, when the file
   fallback kicks in, and how to force the file fallback for
   headless use. Cross-link to the deprecation policy for the
   0600 file itself (it's still supported in 0.6.0, deprecated
   in 0.7.0, removed in 0.8.0 — assuming #14's PR goes through
   the deprecation cycle).

### Email-delivered password reset

17. **Mail provider abstraction + a default SMTP backend.**
   *L, P1.* `backend/mail.py` defines a `Mailer` protocol with
   two implementations:
     - `SMTPMailer`: reads `SMTP_HOST`, `SMTP_PORT`,
       `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM` from env.
       Uses Python's `smtplib` (stdlib, no new dep). Supports
       STARTTLS and implicit TLS. Tested against Gmail SMTP,
       Mailgun, and a local `python -m smtpd`.
     - `LoggingMailer`: writes the rendered email to the
       structured logger instead of sending it. Used in tests
       and as the default when `SMTP_HOST` is unset (so a
       self-hoster who hasn't configured mail yet still gets
       password reset — the reset link lands in the app's log
       stream, which is the same place they look for other
       operational signals).

   The protocol is small — `send(to, subject, body) -> None` and
   `send_template(to, template, context) -> None`. Templates
   live in `backend/templates/email/*.j2` (Jinja2, already a
   FastAPI transitive dep).

18. **Wire the password reset flow to the mailer.**
   *M, P1.* Replace the 0.5.0 admin-mediated reset (the
   `POST /admin/users/{id}/reset-password` flow) with a
   self-serve flow:
     - `POST /auth/password-reset` (public) accepts an email,
       mints a single-use reset token (15 min TTL), and emails
       it to the user. The endpoint always returns 204, even
       if the email doesn't exist, to prevent account
       enumeration.
     - `POST /auth/password-reset/confirm` (public) accepts
       the token + a new password, validates, sets the
       password, invalidates all active sessions for the
       user, and audits.
     - The admin-mediated endpoint becomes
       `POST /admin/users/{id}/reset-password` (admin only)
       which does the same flow but emails the user *via
       the admin's* SMTP config — useful for the "admin
       rotates a compromised account" case where the user
       can't receive email. **This stays**; it's not
       deprecated.

   The 0.5.0 docs (`docs/security.md` and the 0.5.0 plan
   item #25) flagged "admin-mediated reset is a 0.6.0
   follow-up when a mail provider is added." That's this
   item.

19. **Email template for the password reset.**
   *S, P1.* `backend/templates/email/password-reset.j2`
   renders the reset link with the right hostname
   (`PUBLIC_URL` env var, defaulting to the request's
   origin), a 24-hour validity note, and a one-line "if
   you didn't ask for this, ignore this email" footer.
   Plain text only — no HTML email. The terminal-aesthetic
   brand stays consistent.

20. **Document the mail config in the self-host guide.**
   *S, P2.* `docs/self-host.md` grows a "Email config"
   section: which env vars to set, how to test with
   `LoggingMailer` (default), when to use a transactional
   mail provider vs. a personal Gmail, and a link to
   `docs/security-support.md` for the "what if my SMTP
   creds leak" question (the answer is: rotate the SMTP
   password, the `provider_keys` are not affected, but
   audit log entries from the leak window are preserved).

**Slice 3 exit criteria:** All 7 items merged. The CLI uses
the OS keyring on a developer laptop (verified by a quick
sanity test) and falls back to the 0600 file on a headless
server (also verified). The password reset flow works
end-to-end with the `LoggingMailer` (the link appears in
the structured log) and with a real SMTP server (verified
against Mailgun or a local `smtpd`). The
`STANDUP_API_TOKEN` → `STANDUP_API_KEY` rename is the
only entry in the new `### Deprecated` section of the
CHANGELOG.

After 0.6.0 the project will be:

  contract; a written policy is the promise; a deprecation
  gate is the enforcement.
- **Operationally honest.** Security support windows,
  vulnerability response times, and a published advisory
  process.
- **User-friendly enough for 1.0.0.** Keyring integration
  and email-delivered password reset close the two biggest
  UX gaps between "internal tool" and "polished product".

of the 0.6.0 stable surface. The 0.6.0 plan's `*` items
(those marked with a `*` rather than a number) are
informational — they exist to flag scope cuts, not as work
items.

## Notes on slicing

- **Slice 1 is mechanical.** It's the boring PR. It's also
  the one that makes slice 2's policy enforceable, so it has
  to land first.
- **Slice 2 is framing.** It's mostly docs. The code change
  (#9: deprecation markers) is small and only exists to
  demonstrate the policy.
- **Slice 3 is earnest.** It's the one that produces user-
  visible improvement. It can land independently of slice 2
  if slice 2's docs aren't ready, but I recommend shipping
  them in order so the deprecation markers in slice 3 go
  through the new procedure (eating our own cooking, again).

If 0.6.0 ships in the proposed order, the resulting 1.0.0
plan will be: "add organisations on top of the 0.6.0
surface, then add OIDC on top of orgs." Both well-scoped.
Neither requires breaking the API stability contract.
