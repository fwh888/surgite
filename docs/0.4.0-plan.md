# 0.4.0 Plan

Targeted at **v0.4.0**. Builds on the 0.3.0 baseline, which closed out the
performance & UI/UX audit
([performance-ui-audit.md](performance-ui-audit.md)) — every item 1–16 is
shipped or in review. 0.4.0 picks up the work that audit didn't cover:
feature work, operational hardening, and the gaps that surfaced once the
audit's perf wins landed.

The plan is organised by theme rather than by file, with each item carrying
an effort estimate (**S** ≤ half a day, **M** = 1–2 days, **L** = 3+ days)
and a priority (**P1** = blocking for 1.0.0, **P2** = should land in 0.4.0,
**P3** = nice-to-have, defer if needed).

---

## Status (in this release)

### Code & process hygiene

The first three items are housekeeping that makes the rest of 0.4.0 easier
to ship. None of them add user-facing features; all of them make the next
six weeks of work go faster.

1. **Replace the missing `docs/production-readiness-plan.md` link** — *S, P1*
   `AGENTS.md:90` and `README.md:136` still point at
   `docs/production-readiness-plan.md`, deleted during 0.2.0 cleanup
   (`docs/perf-audit` was the replacement). Update both references to point
   at `docs/0.4.0-plan.md` (this file) as the canonical roadmap, and add a
   short pointer at the top of `docs/performance-ui-audit.md` noting that
   the 0.3.0 release closed it. Closes a documentation rot hole that
   every new contributor will trip over.

### Architecture & infrastructure

2. **Scheduled background ingest** — *M, P1*
   `README.md:103` advertises `INGEST_INTERVAL=300` as if a background sync
   job exists; it doesn't. The web UI's "last_ingested_at" timestamp is
   only updated when a user clicks *generate* (which triggers an
   ad-hoc ingest). Add a tiny scheduler (asyncio task in the FastAPI
   lifespan, or an `apscheduler` job) that, every `INGEST_INTERVAL`
   seconds, runs `_ingest_all_repos()` over all registered repos with no
   date filter. Remove the ad-hoc ingest from the `/summary` request path
   entirely — `/summary` should be a pure read against the DB, with the
   scheduler owning freshness. The TTL cache in `api.py:30-36` is a
   band-aid over the missing scheduler and should be deleted at the same
   time. Removes the last reason the `/summary` endpoint does any network
   I/O, and means a user opening the app gets fresh data on the first
   click without paying the fetch cost.

3. **Decouple the AI summary from the request threadpool** — *L, P1*
   `api.py:317-406` runs the per-repo LLM calls on FastAPI's default
   threadpool (`_MAX_PARALLEL_SUMMARIES=4` workers in
   `summarizer.py:19`). With 10 concurrent users generating summaries,
   the threadpool exhausts and `/health` starts timing out. Convert
   `summary` to `async def`, run the provider HTTP calls through
   `httpx.AsyncClient`, and keep the per-repo fan-out in
   `asyncio.gather`. Drop the synchronous `ThreadPoolExecutor` in
   `summarizer.generate_summary_per_repo` in favour of an async version.
   `requests` is no longer needed by the summarizer — switch the
   `httpx` import and remove `requests` from `pyproject.toml` (also
   pick up `httpx`'s built-in timeouts so the magic `_TIMEOUT=120`
   constant can move to a per-call parameter).

4. **Streaming AI summaries** — *M, P2*
   With (3) in place, switch the per-repo and combined calls to
   `stream=True` on the provider and return a `StreamingResponse` of
   `data: …` SSE events. `SummaryPanel.svelte` already manages a
   spinner and an `AbortController`; add a small text-delta handler so
   the cards fill in as the LLM emits tokens. Cuts perceived latency
   to "first token" (~1–2 s on Haiku) and lets the user cancel a slow
   summary without waiting for the whole response.

5. **Delete `commit_log` from `_query_commits` payload** — *S, P2*
   `/summary` returns the full `commits` list in its response
   (`api.py:400`). For a 30-day window across 10 repos that's hundreds
   of KB of data the web UI never renders — `SummaryPanel.svelte` uses
   `by_repo` for the counts and `log_by_repo` for the per-repo text,
   and only inspects individual commits in the empty-state branch. Add
   a `commits=false` default query param to suppress the list; have
   the UI pass it. The list is still available via `/commits` for
   anyone who actually wants it. Reduces the typical `/summary` payload
   by 90%+.

### User-facing features

6. **Shareable summary links** — *M, P2*
   The 0.3.0 export-to-file works for personal use, but a
   standup-gen user often pastes their summary into Slack/Teams/Jira.
   Add a "Copy as Markdown" button (alongside the existing "Copy" which
   is plain text) and a "Copy share link" button that POSTs the
   current summary's parameters (repo, range, author, ai settings) to
   `/summaries` and returns a short slug. The slug resolves to a
   read-only `/s/{slug}` route that re-runs the same query and shows
   the result. No auth for now — the slug is the secret. Migration
   adds a `summaries` table (slug, params JSON, created_at,
   expires_at) and a periodic cleanup job deletes slugs past
   `expires_at` (default 7 days).

7. **Per-repo prompt settings override** — *M, P2*
   `prompt_settings` is currently a single row (`id=1`,
   `db.py:48-61`) that affects all repos. Some users (Nick included,
   per the v0.2.0 changelog) will want different tones/roles for
   different repos — a casual tone for personal projects, formal for
   work. Add a `repo_id` FK to `prompt_settings`, drop the singleton
   pattern, and have the `/summary` endpoint look up settings by
   `(repo_id, None)` falling back to `(None, None)` for the global
   default. The `PromptSettings.svelte` panel gets a repo selector at
   the top; the API gets a `repo_id` query param on the GET/PUT
   endpoints. Migration backfills the existing global row to
   `repo_id=NULL`.

8. **CLI: read from registered repos** — *M, P2*
   `standup` currently only operates on a local path
   (`backend/standup.py:14`). Users who have registered repos in the
   web app can't reuse them from the CLI without re-typing the URL.
   Add a `standup --registered <name>` mode that talks to a running
   standup-gen API (URL from `STANDUP_API_URL`, optional token from
   `STANDUP_API_TOKEN`) and pulls the same data the web UI would. The
   `--output` flag already supports writing to a file or stdout; this
   is purely about getting the same data the web app has, locally.

9. **Webhook: post summaries to Slack/Teams/Discord** — *L, P3*
   The "Copy share link" feature (item 6) is the foundation; the webhook
   is the next step. Per-repo webhook config (URL, format) stored on
   `repos` (`webhook_url`, `webhook_format` columns). After a
   successful `/summary` with `ai=true`, optionally POST a formatted
   message. Defer to a 0.4.x point release if 0.4.0 is already
   feature-heavy.

### Operational hardening

10. **Structured logging** — *S, P1*
    The app uses stdlib `logging` with `log.warning` calls
    (`api.py:23, 68` etc.) but no format config and no log levels set
    in code. Add `logging.basicConfig(level=os.getenv("LOG_LEVEL",
    "INFO"))` at app startup, JSON formatter when `LOG_FORMAT=json`,
    and include `repo`/`since`/`until` fields in the ingest log lines
    as structured extras. Makes the container's stdout greppable in
    Loki/journalctl and ready for a log shipper if the user adds one.

11. **Per-IP rate limit on `/summary`** — *S, P1*
    `/summary?ai=true` is an expensive endpoint (network fetch + N LLM
    calls). Add a tiny in-memory token bucket keyed on client IP,
    ~5 requests per minute. A misconfigured script or accidental
    button-mash shouldn't be able to rack up $5 of API spend. Uses
    `slowapi` (1 dep) or a 30-line hand-rolled middleware if we want
    to stay dep-free. Either is fine; pick `slowapi` if the user
    doesn't object to one more transitive.

12. **Health endpoint depth** — *S, P2*
    `/health` (api.py:215) only checks DB connectivity. The `db`
    healthcheck in `docker-compose.yml:11-15` only checks
    `pg_isready`. Add a `/health/deep` endpoint that does a `git
    fetch` against one registered repo (or, if none registered, a no-op
    200) and a provider-key reachability check (skip the key test if
    none configured). Returns 200 with `{db: ok, git: ok, providers:
    {anthropic: ok|missing_key|unreachable, …}}` or 503 with the
    failing component. Lets the user wire Uptime Kuma to it
    meaningfully.

13. **Backup & restore recipe** — *S, P1*
    Standup-gen is now the system of record for commit history across
    the user's registered repos. The `pgdata` volume in
    `docker-compose.yml:11` is the only persistent state. Add a
    `scripts/backup.sh` that `pg_dump`s the database, gzip-compresses,
    and writes to a configurable `BACKUP_DIR` (default
    `/var/standup/backups`) with a date-stamped filename. Add a
    matching `scripts/restore.sh`. Document both in README. Cheap
    insurance and gives the user a clear hook for their PBS job
    (`vmid 207` per the homelab memory).

## What 0.4.0 explicitly does *not* include

- **Multi-user auth.** Not on the roadmap for 0.4.0 or 1.0.0; the
  threat model is "single user, trusted network, behind Traefik" and
  adding auth is a separate project.
- **Vector search / semantic commit lookup.** Tempting, but a
  different product. Out of scope.
- **A v2 SvelteKit rewrite.** `docs/v2-svelte-plan.md` was deleted in
  0.2.0; the v0.2.0 work shipped the equivalent polish without the
  rewrite. No motion here.
- **New LLM providers** beyond Anthropic / Groq / DeepSeek. The
  abstract `Provider` interface makes adding one trivial; a new
  provider should arrive with a real user need, not as roadmap
  padding.

## Sequencing

If 0.4.0 has to ship in a hurry, the minimum viable cut is items **1,
2, 3, 10, 11, 13** — the P1 hygiene, infrastructure, and ops items
that don't add user-facing features but make the rest of the work
sustainable. Items 4–8 are the visible user-facing 0.4.0 release. Item
9 is post-0.4.0.

| Group | Items | Why this group |
| --- | --- | --- |
| Foundation (do first) | 1, 2, 3, 10, 11, 13 | Hygiene + ops. P1. Unblocks everything else. |
| User-facing (the release) | 4, 5, 6, 7, 8, 12 | The visible delta. 0.4.0 is "real features". |
| Optional | 9, 14, 15 | Defer to 0.4.x or 0.5.0 as time allows. |

## Open questions for the user

- (item 6) Is a 7-day slug TTL the right default, or should it be
  configurable per-share?
- (item 8) Is the CLI ↔ API auth model a static token in env, or
  something stronger (signed JWT, OAuth)? The current standup-gen has
  no auth at all, so this would be the first auth surface.
- (item 11) `slowapi` vs. a 30-line in-process bucket. The dep is
  small but it pulls in `limits`, and the project principles lean
  minimalist.
- (item 7) Should the global prompt settings row be preserved on
  migration, or wiped to start fresh with per-repo settings?

These should be answered (or explicitly deferred) before the
implementation PRs land.
